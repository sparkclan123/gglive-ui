# หน้าสมาชิก Fantasy และหลาย Gameweek พร้อมกัน

Status: Design approved; implementation authorized. No Docker build or deployment.

## ขอบเขตและข้อกำหนด

- ออกแบบหน้าสมาชิกแบบ mobile first ให้เป็นแอปฟุตบอลแฟนตาซี สีแดงเป็นหลัก ส้มเป็นสีเสริม พื้นดำ ตามภาพอ้างอิงของผู้ใช้
- ไม่เพิ่มโลโก้สโมสรแยกเป็นไอคอน ใช้ชื่อและตัวย่อ ส่วนเสื้อจัดทีมใช้ภาพเดิมของระบบ รวมผู้รักษาประตูและช่องว่าง ตามคำแก้ไขล่าสุดของผู้ใช้
- ใช้ข้อมูลจริงจาก member API เพื่อประกอบการดูแบบ ภาพสร้างขึ้นใช้เฉพาะส่วนประกอบที่จำเป็น ไม่ใช้แทนข้อมูลการแข่งขัน
- เตรียมให้เปลี่ยนแบรนด์เฉพาะหน้าสมาชิกได้จาก configuration กลาง ได้แก่ชื่อ wordmark สีหลัก รูปประกอบ และ contact assets หลีกเลี่ยงการฝังชื่อ/สีซ้ำในแต่ละหน้า
- เปิดหลาย Gameweek พร้อมกันได้ ทั้งใน Season เดียวและคนละ Season สมาชิกเลือกเล่นรอบที่เปิดได้โดยรายชื่อทีมและนักเตะไม่ปนกัน
- หนึ่ง Gameweek ยังใช้กับโหมดปกติและ VIP ร่วมกันเหมือนเดิม ไม่เพิ่มการแข่งขันอีกประเภท
- คง workflow และกติกาที่ใช้อยู่ รวมถึงคะแนน รางวัล ตั๋ว เงื่อนไขจัดทีม การดูทีม และการแก้ไข ไม่ปรับกฎที่ไม่เกี่ยวกับการแยก Gameweek
- ไม่ build Docker ไม่ deploy และไม่เปลี่ยนฐานข้อมูลจริงในงานรอบนี้ ข้อมูลสำหรับ prototype อ่านด้วยบัญชีที่ผู้ใช้อนุญาตเท่านั้น ไม่ใส่รหัสผ่านหรือ token ในโค้ด หน้าเว็บ หรือไฟล์เอกสาร

## สิ่งที่พบในระบบเดิม

`GameWeek` และ `PlayerGameWeek` รองรับหลายรอบอยู่แล้ว การสร้างรอบบันทึกสำเนานักเตะตามรอบและ Season แต่ member discovery ใช้ `FirstGameWeekActives` คืนรอบเดียว การแข่งขันบางหน้ากลับใช้รอบที่ ID ล่าสุด

รายการทีม member และตัวกรองในหน้ากรอกคะแนน admin อ่าน `teams.is_close` ส่วนกลาง จึงอาจซ่อนทีมของรอบเก่าเมื่อแอดมินเปิดทีมอีกชุดเพื่อสร้างรอบใหม่ ส่วนข้อมูลนักเตะของรอบเก่ายังมีอยู่

หน้าสร้างทีมใช้ Season ล่าสุดจาก store ในการนำทาง และ state นักเตะที่เลือกเป็น state ร่วม จึงต้องส่งและตรวจสอบตัวตนของรอบให้ชัดเจนเมื่อเปลี่ยน Gameweek

อ้างอิงหลัก: `premierleague/services/queryGameWeek.go`, `premierleague/services/queryTeams.go`, `premierleague-bo/controllers/GameWeekCreateController.go`, `premierleague-bo/controllers/GameWeekController.go`, `src/components/season/SeasonSelect.vue`, `src/components/season/SeasonSelectVip.vue`, `src/store/modules/GameWeek.js`.

## แนวทางที่พิจารณา

1. ใช้การเปิด–ปิดทีมจากเมนูเดิมเท่านั้นก่อนสร้างรอบ แล้วตรึงข้อมูลรอบนั้น: เปลี่ยน workflow น้อยที่สุด แต่แอดมินต้องสลับชุดทีมส่วนกลางทุกครั้งและตรวจย้อนหลังยาก
2. เพิ่มส่วนเลือกทีมในฟอร์มสร้างเดิม โดยเลือกทีมที่เปิดอยู่ให้ก่อน: ยังสร้างแบบเดิมได้ พร้อมตรวจและปรับเฉพาะรอบได้ **ผู้ใช้เลือกแนวทางนี้**
3. เพิ่มระบบการแข่งขัน/ตาราง membership ใหม่ทั้งชุด: งานและการย้ายข้อมูลมากกว่าที่จำเป็น จึงไม่เลือก

ใช้ PlayerGameWeek เดิมเป็นแหล่งข้อมูลชุดนักเตะของรอบ และหา distinct club IDs จากข้อมูลนี้ ไม่ต้องเพิ่มตารางผูกทีมใหม่เพียงเพื่อ feature นี้

## พฤติกรรมของ Gameweek

### หลังบ้าน

ฟอร์มสร้างยังมี Season, หมายเลข, ชื่อ, สถานะ, เวลาเปิดและปิดเหมือนเดิม เพิ่มส่วน “ทีมที่ใช้ในรอบนี้” พร้อมจำนวนที่เลือกและปุ่ม “ใช้ทีมที่เปิดอยู่” ค่าเริ่มต้นตรงกับเมนูจัดการทีมเดิม แสดงรายชื่อ/ตัวย่อแทนโลโก้ในตัวอย่าง

ส่งรายการ club IDs ไปกับ request เดิม ตรวจทีมมีอยู่และนักเตะอยู่ใน Season ที่เลือกก่อนสร้าง snapshot ภายใน transaction เดียว ถ้าไม่ส่งรายการเพื่อรองรับ client เก่า ให้ใช้ทีมที่เปิดอยู่ตามพฤติกรรมเดิม; ถ้าส่งรายการว่างโดยตั้งใจ ให้แจ้งข้อผิดพลาดและไม่สร้างรอบว่าง

การเปลี่ยนสถานะทีมส่วนกลางหลังสร้าง ไม่มีผลต่อสโมสรหรือนักเตะของ Gameweek เดิม ตัวกรองในหน้ากรอกคะแนนและจัดการทีมต้องมาจากรอบนั้น การเปลี่ยนสมาชิกของรอบหลังสร้างไม่เพิ่มเป็นฟีเจอร์ในงานนี้

ระบบกรอกคะแนนและสรุปผลยังทำผ่าน admin ตามเดิม และคำนวณทั้งปกติ/VIP สำหรับ Gameweek ที่เลือก

### สมาชิก

- หน้าเลือกเกมวีคแสดงทุกรอบที่เปิดรับ และรอบที่ยังไม่ถึงเวลาเปิดแยกสถานะชัดเจน เรียงรอบที่ปิดรับก่อนขึ้นก่อน พร้อมชื่อ Season, ชื่อ Gameweek, วันปิดรับ, รางวัล, จำนวนผู้เข้าแข่งและทีมของผู้ใช้ แยกตัวเลขปกติ/VIP
- แท็บปกติ/VIP ยังคงอยู่ รอบหนึ่งใช้ชุดทีมเดียวกัน แต่ข้อมูลสิทธิ์เข้าร่วมและรางวัลแยกตามโหมด
- `game_week_id` ใน route/request เป็นตัวกำหนดรอบ ส่วน Season ใช้จาก Gameweek นั้น ห้ามใช้ Season ล่าสุดอิสระจากรอบ
- แต่ละหน้าที่เกี่ยวข้องใช้รอบที่เลือกเดียวกัน: จัดทีม รายชื่อนักเตะ ตัวกรองสโมสร คะแนน รายการเข้าแข่ง อันดับ รางวัล การคัดลอกทีม และการแข่งขันที่สมาชิกสร้างเอง
- ข้อมูลย้อนหลังยังเข้าถึงได้ตามเดิม ไม่จำกัดให้เหลือเฉพาะรอบที่เปิด
- การเปลี่ยนรอบต้องโหลด pool และล้าง selection ที่ไม่ตรงบริบท หากมีทีมยังไม่บันทึกให้ยืนยันก่อนเปลี่ยน ห้ามมีรายชื่อนักเตะจากรอบเดิมแวบเข้ามาระหว่างโหลด และห้ามคำตอบ request เก่าทับ state ของรอบใหม่
- สิทธิ์แก้ทีมพิจารณาจาก Gameweek ของแต่ละ entry และกฎเดิม ไม่เทียบกับ active ID เพียงตัวเดียว
- Server ตรวจเวลาและสถานะจริงตอนส่ง/แก้ตาม workflow เดิม รวมถึงตรวจว่ารายการนักเตะมาจาก snapshot ของรอบและ Season เดียวกัน ใช้ player identity จาก snapshot และจำกัดการเปลี่ยนกัปตันให้อยู่ในทีมเดียวกัน
- ใช้ cache แยกตาม Gameweek/Season/โหมดเมื่อจำเป็น พร้อมล้างรายการรอบและ cache ที่เกี่ยวข้องเมื่อสร้าง/ปรับ/สรุปผล ไม่อาศัย singleton cache สำหรับ flow ใหม่

### ความเข้ากันได้

คง IDs, snapshots, entries และผลเก่าทั้งหมด หา club membership ของรอบเก่าจาก snapshot ไม่ใช้รายการทีมที่เปิดอยู่ปัจจุบัน APIs เดิมแบบไม่มี ID อาจคง fallback เพื่อรองรับ client เก่า แต่ UI ใหม่ต้องส่ง ID เสมอ ตรวจ endpoint สร้าง Gameweek เก่าใน member service ให้ใช้กฎการสร้างเดียวกันหากยังคงเปิดอยู่

ไม่ทำ backfill หรือเปลี่ยนฐานข้อมูล production จาก prototype นี้ ตรวจ schema จริงก่อนเสนอ migration ใดในขั้นพัฒนา

## พฤติกรรมจัดทีมที่ต้องคง

- งบ 80 และผู้เล่น 11 คน: GK 1, DEF อย่างน้อย 3, MID อย่างน้อย 2, FWD อย่างน้อย 1
- รักษาช่องเลือก 1/5/5/3 ที่มีอยู่ ไม่บังคับ formation ใหม่โดยเข้าใจผิดว่าเลขดังกล่าวเป็นจำนวนผู้เล่นลงสนาม
- เพดานนักเตะต่อสโมสรอ่านจาก `/condition` ไม่ฝังค่า 3 ถาวร
- เลือก/นำออก/เลือกกัปตัน/ล้างทีม/กรอกชื่อทีมไม่เกิน 18 ตัวอักษร และ confirmation ตามเดิม
- ปกติหนึ่งทีมต่อผู้ใช้ต่อรอบ, VIP ใช้หนึ่งตั๋วต่อทีม ตั๋วเป็นยอดกลางของผู้ใช้เหมือนเดิม
- ตัวกรองสโมสร ตำแหน่ง ชื่อ ราคา สถานะพร้อมเล่น จำนวนที่ถูกเลือก และ pagination ต้องยังมีครบ
- คัดลอกทีมของตนเองจากโหมดปกติ/VIP ภายในบริบท Gameweek ที่เลือก และเลือกกัปตันใหม่ตามเดิม
- แก้ไขทันที: เปลี่ยนรายการแล้วบันทึกเป็นครั้ง ๆ; แก้ไขทั้งทีม: มี undo/reset และกดบันทึกครั้งเดียว ต้องคงความต่างของสองโหมด
- ไม่ทำให้ validation ที่ต่างกันอยู่เดิมระหว่าง create/edit กลายเป็นกฎใหม่โดยไม่ได้รับคำขอ งานแยก Gameweek จำกัดการตรวจเพิ่มเติมเฉพาะขอบเขตข้อมูลของรอบ/ทีม

## การตรวจรับเมื่อพัฒนาจริง

1. เปิดรอบ A/B พร้อมกัน ใช้ทีมคนละชุด แล้วทั้งปกติ/VIP แสดงและส่งทีมลงรอบที่เลือกถูกต้อง
2. เปิด–ปิดทีมใน catalog เพื่อเตรียมรอบ C แล้ว A/B ยังแสดงชุดเดิม รวมทั้ง admin กรอกคะแนน
3. URL ข้าม Season, เปลี่ยนรอบรวดเร็ว, reload, back, request เก่ากลับช้า ไม่ทำให้ pool ปนกัน
4. ปฏิเสธ snapshot/player/captain จากรอบหรือทีมอื่น และไม่ตัดตั๋ว/บันทึกบางส่วนเมื่อผิดพลาด
5. รายการของฉัน อันดับ คัดลอก และ self-match ผูกกับรอบเดียวกัน ปกติส่งได้หนึ่งทีมต่อรอบแยกกัน
